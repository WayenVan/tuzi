yazi · crate 层级架构

Yazi 的核心究竟在哪里

Yazi 是一个由 31 个 crate 组成的 Cargo workspace，而不是单一的整体。其中大约三分之一是与 UI 无关的文件管理器内核（文件系统模型、后台任务、监视器）；其余部分则是 ratatui 终端界面、Lua 插件运行时，以及构建在这些之上的两个二进制程序。下面这份拆解，说明了做一个树形文件管理器时，哪些部分可以直接搬用，哪些只值得模仿，哪些该丢掉。

给树形重写的速览结论

直接搬用

yazi-shared、yazi-fs、yazi-vfs、yazi-scheduler、yazi-runner、yazi-watcher —— Url/Cha 文件模型、本地 + SFTP 引擎、后台任务队列、文件系统监视，这些都不关心你的界面是不是树形结构。

照搬模式

yazi-parser 与 yazi-actor 的拆分方式——把一个 Cmd 解析成带类型的 Opt，再执行一个纯函数式的 Actor::act(cx, form) -> Result<Data>——是一种干净的控制器结构，即便你的状态形态完全不同，也值得照着重新实现一遍。

重写结构

yazi-core 里的 Mgr/Tab 假定了三栏布局（父目录 / 当前目录 / 预览），建立在一份带前进后退历史的扁平目录列表之上。树形结构需要的是一棵带每节点展开状态的递归节点树——事件驱动的变更方式可以不变，但底层结构体要换。

v1 阶段跳过

yazi-plugin（mlua 运行时）和 yazi-dds（跨实例发布订阅）都是体量很大、自成一体的子系统，做出第一版能用的树形文件浏览器并不需要它们。

运行时事件循环

一个二进制程序，一个异步任务。所有输入——按键、Lua 里的 ya.emit()、一个跑完的后台任务、一次目录变化——都会变成同一个 mpsc 通道上的一个 Event；随后是一次同步的分发过程来改变状态；最后由一个脏标记决定要不要重绘。

每一层具体做什么

共享内核 —— yazi-shared、yazi-fs、yazi-vfs

yazi-shared 定义了 Url/UrlBuf 位置类型，以及随处可见的 Event/Cmd/Action 基础设施。yazi-fs 在此之上加入了本地磁盘的基础能力：Cha（缓存的元数据）、排序、过滤、回收站、挂载点探测。yazi-vfs 则位于更上层，是可插拔的引擎层——本地与 SFTP 两种后端统一在一套 read_dir/Cha 接口之下，这正是一个不关心具体协议的树形遍历器所需要的抽象。

后台 I/O —— yazi-scheduler、yazi-runner、yazi-watcher

一个用于复制/移动/删除/链接/计算大小的工作线程池，并带进度汇报（yazi-scheduler）；一个"用什么打开"的解析器，负责拉起外部程序（yazi-runner）；以及一个带防抖的本地 + 远程变更通知器（yazi-watcher）。这些都不知道什么是面板、列表或者树，它们只是搬运数据，再通过事件通道汇报结果。

命令层 —— yazi-parser + yazi-actor

每一个按键绑定最终都会解析成一个带字符串/布尔/整数参数的 Cmd。yazi-parser 把它转换成每个动作各自对应的带类型 Opt 结构体（例如 mgr::CdOpt）；yazi-actor 的 Actor trait（yazi-actor/src/actor.rs:7）则把 (Ctx, Opt) 变成一次状态变更。这是一种干净、朴素的控制器模式——即便你的 Opt 类型和状态完全不同，也值得照搬这套结构。

领域状态 —— yazi-core

Core（yazi-core/src/core.rs:8）持有 Mgr（多标签页、yank/paste、查找/过滤）以及每个 Tab（当前目录、父目录、预览、选中项、前进后退历史）。这种形态——三个同步的面板加一个目录历史栈——是 yazi 列表视图特有的设计。树形文件管理器需要的是一整棵持久化的节点图，带展开/折叠状态和惰性加载的子节点；把这个 crate 当作"一个文件管理器需要跟踪哪些状态"的规格说明来读，而不是一个可以直接继承的结构体。

终端与渲染 —— yazi-tty、yazi-term、yazi-emulator、yazi-adapter、yazi-tui、yazi-widgets

原始终端模式、按键/鼠标/粘贴/拖放事件解析、终端模拟器能力探测，以及图像预览协议驱动（kitty/iTerm2/sixel/chafa），这些都与具体布局无关，可以直接复用。yazi-tui 的 Raterm 后端和 yazi-widgets 的输入/滚动组件，是 yazi 自己那套为三栏布局定制的 ratatui 组件库——值得参考，但你多半会自己写一个树形列表组件，而不是直接拿来用。

脚本、IPC 与应用程序 —— yazi-plugin、yazi-dds、yazi-fm、yazi-cli

基于 mlua 的插件运行时（fetcher/previewer/peeker、Lua 编写的 UI 组件），以及用于 ya emit-to 和跨实例状态同步的 Unix socket 发布订阅系统，都是体量庞大、自成一体的子系统——第一版可以先跳过。yazi-fm/yazi-cli 则是你要整体替换掉的组合根：main()（yazi-fm/src/main.rs:12）展示了各 crate 初始化的确切顺序，你自己的二进制程序也应该照此模仿。

建议的提取顺序

  1. 先搬文件模型。引入 yazi-shared、yazi-fs、yazi-vfs（如果需要远程文件系统，再加上 yazi-sftp）。这样在你写第一行树形逻辑之前，就已经有了 Url、Cha、排序，以及一个能用的 read_dir。
  2. 设计你自己的树节点类型。参照目前 Tab/Folder 跟踪的内容（yazi-core/src/tab、yazi-core/src/mgr）——选中项、yank 状态、过滤/查找、排序——但把它们变成递归结构里每个节点各自的字段，子节点惰性加载，而不是每个面板一个扁平的 Vec<File>。
  3. 照搬事件的形状，而不是代码本身。一个 Event 枚举、一个 mpsc 通道、一个按 layer + 动作名匹配的 dispatcher、返回 Result<Data> 并翻转脏标记的 actor——yazi-fm 整个 App::serve() 循环用大约四个类型就能说清楚。
  4. 尽早接入后台任务。引入 yazi-scheduler + yazi-runner，让复制/移动/删除和"用什么打开"从第一天起就不会卡住渲染循环——等树形界面已经做出来了再补异步 I/O，代价会大得多。
  5. 树渲染出来之后再加 yazi-watcher，这样外部变化（git 操作、其他进程）才能精确地让对应子树失效，而不是每次都强制整体重新加载。
  6. yazi-plugin/yazi-dds 留到后面。上面提到的所有部分都不依赖它们；等核心的树形体验做扎实了，再考虑加入 Lua 脚本能力。
